# 家庭级全能多源搜索 MCP 设计

日期：2026-07-24

## 1. 目标

在家庭 Mac 上部署一个通过 `mcp-search.bri-king.com` 访问的多源研究服务，供 5–10 位家庭成员使用。每个问题先并发调用八个通用来源，并为每个来源同时执行通用与生态定向双通道搜索，再由内置 AI 根据已发现的实体与意图自动规划延伸搜索。服务返回结构化结论、证据、来源、冲突、缺口和置信度，ZCode 或其他客户端 AI 负责最终面向用户的整理表达。

本系统追求“商用级可用性”，具体定义为：

- 对 5–10 位家庭用户提供稳定的鉴权、排队、限流和故障隔离。
- API 来源不因浏览器来源排队而被阻塞。
- 单一来源失败时仍返回部分有效结果。
- 所有重要结论尽可能关联可检查的来源。
- 明确区分已证实、交叉支持、单一来源、平台观察和未验证内容。
- 在家庭 Mac 开机、网络和 Cloudflare Tunnel 正常的前提下，以月度 99% 服务可用率为运行目标；这不是对外部搜索平台可用率或信息真实性的承诺。

## 2. 已确认的产品原则

1. 采用“网关 + 调度器 + Provider Worker 池”的方案 B。
2. 每次输入一个问题，第一轮立即并发八个通用来源，并为每个来源同时执行通用与生态定向搜索。
3. 服务端内置 AI，自动完成实体识别、意图猜测、关键词规划、延伸维度选择、冲突识别和证据整理。
4. 不要求用户先精确说明想查什么。系统先理解“这是什么”，再根据对象类型补充通常最有价值的维度。
5. 服务端返回证据化、结构化的数据，不把模型生成文本当作事实本身。
6. 调用方 AI 可以基于结构化结果再次组织语言，但不得丢失来源、冲突和不确定性。
7. 豆包在国内短视频、消费热度、团购和现场体验类问题上具有更高先验权重；该权重不适用于法人、登记、司法、政策等必须优先采用官方原始资料的事实。
8. 系统提供置信度说明，但不承诺搜索结果绝对真实或完整。

## 3. 非目标

第一版不包含以下行为：

- 绕过验证码、登录验证、平台限制或账号风控。
- 用一个消费级账号并发服务多个浏览器任务。
- 把 AI 自身记忆当作真实性证明。
- 把搜索结果包装成法律、投资、医疗或安全保证。
- 在客户端 Skill、Git 仓库、安装包或日志中分发上游 API Key、Cookie 或浏览器 Profile。
- 对未登录、付费墙、私密群组或无授权内容进行访问。
- 通过家庭共享千问执行下单、预订、支付、充值、退款、转账或账户变更。
- 通过家庭共享服务查询任何人的支付宝、社保、公积金、税务、身份、护照或其他个人官方记录；未来若支持，必须采用逐用户授权与显式确认。

## 4. 域名与部署拓扑

现有 Cloudflare Tunnel：

- Tunnel：`ai-site`
- `ai.bri-king.com` → `http://localhost:8001`
- `ai-gpt.bri-king.com` → `http://localhost:8317`

新增独立入口：

- `mcp-search.bri-king.com` → `http://127.0.0.1:8765`

服务仅监听回环地址，不直接暴露本机端口、CDP 端口或浏览器调试接口。Cloudflare Tunnel 负责公网 HTTPS；应用层仍必须验证客户端访问 Key，不能把“知道域名”视为授权。

```text
ZCode MCP Client ─────────────┐
WorkBuddy Remote Skill ───────┼─ HTTPS + Bearer Key
其他家庭 AI / Script ────────┘
                                      │
                         mcp-search.bri-king.com
                                      │
                       Search Gateway :8765
                                      │
                 Planner / Scheduler / Job Store
                       │                    │
                API Provider Pool    Browser Account Queue
                       │                    │
               Evidence Normalizer / Claim Ledger
                                      │
                         Structured Research Result
```

服务和浏览器 Worker 由独立 LaunchAgent 管理，崩溃后自动拉起；日志轮转并移除请求中的密钥、Cookie、授权头和浏览器状态。

## 5. 来源矩阵

### 5.1 八个通用来源

| 来源 | 通用职责 | 优先补充的信息 | 运行方式 |
| --- | --- | --- | --- |
| Tavily | 全球网页快速检索 | 官方网站、新闻、报道、背景资料 | 异步 HTTP API |
| Exa | 语义搜索和相似页面发现 | 高相关长文、研究页、权威页面 | 异步 API/MCP Adapter |
| Gemini | 海外网页与多媒体理解 | YouTube、Reddit、海外长视频、英文资料 | 隔离 Profile 浏览器 + CDP 独立页面 |
| Grok | 实时海外舆情 | X/Twitter 帖子、突发话题、实时观点 | 隔离 Profile 浏览器 + CDP 独立页面 |
| 豆包 | 国内生活消费与短视频生态 | 抖音、头条、国内短视频、团购、现场热度、用户体验 | 豆包桌面版 CDP 独立页面 |
| 元宝 | 腾讯内容生态 | 微信公众号、视频号、腾讯生态文章和讨论 | 每任务独立 BrowserContext |
| 文心 | 国内通用网页基础兜底 | 百度百科、政府网站、政务信息、国内通用网页 | 每任务独立 BrowserContext |
| 千问 | 阿里公开生态只读发现 | 淘宝价格、飞猪旅游、高德路线、饿了么本地生活 | 隔离 Profile 浏览器 + CDP 独立页面；禁止交易和个人记录 |

“通用来源”表示每一轮基础搜索都会收到针对同一研究目标定制的查询，而不是把相同原句机械复制八次。

### 5.2 社区定向来源

第一版社区 Adapter：

- GitHub：仓库、代码、Issue、PR、Discussion、Release、Commit。
- Hacker News：技术项目和创业社区讨论。
- Stack Exchange：技术问题与专家回答。
- Reddit：通过可用的官方或合规检索方式发现社区讨论。
- YouTube：通过 Gemini 或可用的官方检索接口获取视频、频道和时间信息。
- X/Twitter：通过 Grok Live Search 或可用的官方接口获取实时舆情。
- 抖音/头条：由豆包定向检索团购、短视频、探店、活动、客流和评论信号。
- 微信公众号/视频号：由元宝定向检索公众号文章、视频号内容和腾讯生态讨论。
- 百度百科/政务：由文心定向检索实体基础资料和国内官方网页。
- 淘宝/飞猪/高德/饿了么：由千问只读检索公开商品价格、旅游产品、路线和本地生活线索。

八个 Provider 均同时启动 `general` 与 `specialized` 两条查询通道。浏览器来源通过 20 个逻辑槽位和实测 `active_limit` 排队；每个任务使用新的 Page 或 BrowserContext，结束后销毁，不能继承其他家庭成员的会话历史。

## 6. 自动研究规划

### 6.1 输入规范化

服务首先生成 `ResearchBrief`：

- 原始问题。
- 规范化实体名称及别名。
- 可能的实体类型。
- 时间范围、地域、语言和新鲜度要求。
- 明示意图。
- 推断意图及其置信度。
- 必须回答的基础维度。
- 可选延伸维度。
- 禁止猜测或需要官方证据的字段。

若实体存在明显歧义，服务同时搜索最可能的 2–3 个候选，并在结果中明确列出消歧证据，而不是静默选择一个。

### 6.2 第一轮：对象识别与全景搜索

第一轮固定启动：

- 八个通用 Provider 的 `general` Job。
- 八个 Provider 的 `specialized` 生态定向 Job。
- 官方域名、政府登记或项目官网的定向查询。

第一轮目标：

1. 确定对象是什么。
2. 确定所在地、主体、类别和主要业务。
3. 发现用户最可能关心的搜索维度。
4. 收集可用于第二轮规划的实体、别名、地址、公司名、项目名、账号名和官方链接。

### 6.3 第二轮：按对象类型自动延伸

Planner 根据第一轮证据选择延伸维度，不采用无限关键词扩张。默认最多选择 4–8 个高价值维度，并允许客户端通过 `depth` 控制预算。

常见对象类型与延伸维度：

#### 地点、园区、景区或文创项目

- 基础资料、地址、开放时间、交通和停车。
- 项目历史、运营主体、产权或投资方。
- 法人、工商登记和关联公司。
- 招商、租金、品牌入驻和商业模式。
- 客流量、热度趋势、节假日拥挤程度。
- 抖音团购券、门票、套餐和近期活动。
- 游玩路线、适合人群、预计停留时间和避坑建议。
- 用户评价、现场照片/视频信号和争议。
- 政策、消防、行政处罚、诉讼等风险信号。

#### 公司、品牌或产品

- 官网、工商主体、法人和股权关联。
- 产品功能、定价、用户群和竞争对手。
- GitHub、技术栈、版本、Issue 和维护活跃度。
- 融资、投资方、经营风险和舆情。
- 国内外用户评价、投诉和真实使用场景。

#### 人物或事件

- 身份和时间线。
- 原始声明、官方资料和一手记录。
- 国内外媒体覆盖。
- X、Reddit、抖音、公众号等社区舆情。
- 支持与反对证据、争议点和未证实说法。

#### 旅游问题

- 目的地基础信息。
- 到达方式、交通、天气和季节。
- 门票、团购、预约和开放时间。
- 一日/两日路线、附近餐饮住宿。
- 抖音探店和现场热度。
- 公众号攻略和近期活动。
- 海外游客评价或视频资料。
- 安全、拥堵、临时关闭等实时信号。

### 6.4 示例：“1970 文创园”

用户仅输入“1970 文创园”时：

1. 第一轮并发识别其准确名称、城市、地址、运营主体和项目类型。
2. 豆包重点搜索抖音/头条中的探店、团购、近期活动、客流和现场体验。
3. 元宝重点搜索公众号/视频号中的项目介绍、活动、招商和攻略。
4. 文心重点搜索百度百科、政务、规划和国内网页。
5. Grok 搜索 X 上是否有实时海外游客或事件讨论。
6. Gemini 搜索 YouTube、Reddit、海外长视频和英文资料。
7. 千问只读搜索淘宝公开价格、飞猪旅游产品、高德路线和饿了么本地生活线索，不执行任何交易或个人记录查询。
8. Tavily、Exa 搜索官网、新闻、项目背景和权威长文。
9. 若识别为可游玩的商业文创园，自动追加：运营/投资主体、法人、实际控制人、客流、团购、活动、交通停车、游玩路线、餐饮、适合人群和风险提示。
10. 若第一轮显示它主要是招商项目而不是景区，则提高投资、主体、入驻品牌和商业经营维度的优先级，降低旅游攻略权重。

这实现“猜你想搜什么”，但所有推断意图都必须在返回数据中可见，调用方可以删除或追加维度。

## 7. AI 组件

当前远程第一版使用确定性的 `ResearchBrief`、Provider Router、证据归一化和 Evidence Digest。以下模型配置属于可选后续增强；聊天中出现过的旧 Key 轮换前不得启用：

- OpenAI 兼容 Base URL：`https://opencode.ai/zen/go/v1`
- 模型：`deepseek-v4-flash`
- 凭证从本机私密环境或 Keychain 注入，不写入仓库或设计文档。

模型承担：

1. `Planner`：实体识别、意图推断、搜索维度和查询词生成。
2. `Router`：为每个 Provider 生成适合其生态的查询。
3. `Verifier`：把证据映射到具体 Claim，发现冲突、范围差异和日期差异。
4. `Synthesizer`：生成简短的服务端摘要以及结构化结果。

确定性代码承担：

- URL 规范化与去重。
- 来源域名识别。
- Provider 状态、超时和错误记录。
- Claim 与 Citation 的引用完整性检查。
- 置信度数值计算。
- 缓存、队列、限流和权限。

如果模型不可用，服务仍返回原始 Provider 结果、规范化引用和确定性摘要，并明确标记“AI 规划/验证未完成”。

## 8. 证据与置信度

### 8.1 证据类别

- `official_primary`：政府、工商、法院、项目官网、维护者发布、原始公告。
- `direct_platform`：原始视频、帖子、Issue、PR、Release、公众号文章。
- `reputable_secondary`：可信媒体、机构报告、专业文章。
- `community_observation`：用户评论、论坛讨论、短视频体验、社交舆情。
- `search_summary`：搜索平台或模型生成但缺少可访问原始链接的摘要。
- `unresolved_lead`：值得继续搜索但尚未取得原始证据的线索。

### 8.2 Provider 先验权重

权重按“问题维度”而不是简单按平台固定：

- 国内短视频、团购、探店、现场热度：豆包高权重。
- 微信公众号、视频号、腾讯生态：元宝高权重。
- X 实时舆情：Grok 高权重。
- YouTube、Reddit、海外长视频：Gemini 高权重。
- 百度百科、政务、国内通用网页发现：文心较高权重。
- 淘宝价格、飞猪产品、高德路线、饿了么本地生活：千问提供公开生态发现线索；交易和个人记录始终禁止。
- 法人、工商、司法、政策：官方原始网站权重最高，任何模型摘要都不能覆盖官方证据。
- GitHub 项目状态：仓库、Release、Commit、Issue 和维护者声明权重最高。

豆包可以提高“国内消费现场信号”的置信度，但单个豆包回答不能把法人、投资额、处罚或客流数字直接提升为高置信事实。

### 8.3 Claim 置信度

每条 Claim 返回：

- `confidence_score`：0–1。
- `confidence_label`：high / medium / low / unverified。
- 支持该 Claim 的独立文档数量。
- 支持 Provider 数量。
- 是否存在官方原始证据。
- 是否存在来源冲突。
- 数据的新鲜度和适用范围。
- 置信度说明。

独立 Provider 发现同一个 URL 只算一个证据文档。模型生成的摘要不能与其引用的原始页面算作两个独立来源。

高置信度通常要求：

- 一份适用范围明确的官方原始证据；或
- 至少两份相互独立、内容一致且日期适用的可靠证据。

客流量、营收、投资额、团购销量等数字必须标注日期、口径和来源。不同口径数字不能简单平均。

## 9. 返回格式

MCP 和 REST 共用同一个结构化结果模型：

```json
{
  "request_id": "...",
  "status": "complete|partial|running",
  "original_query": "1970文创园",
  "resolved_entities": [],
  "inferred_intents": [],
  "research_dimensions": [],
  "summary": "...",
  "claims": [
    {
      "claim": "...",
      "confidence_score": 0.86,
      "confidence_label": "high",
      "explanation": "...",
      "citation_ids": ["src_1", "src_4"],
      "conflicts": []
    }
  ],
  "sources": [],
  "provider_observations": [],
  "conflicts": [],
  "unknowns": [],
  "suggested_followups": [],
  "provider_status": {},
  "timing": {},
  "disclaimer": "置信度表示当前证据支持程度，不构成真实性、完整性或专业建议保证。"
}
```

`provider_observations` 保存豆包、元宝、文心等无法取得稳定原始 URL 时的平台观察，但不能伪装成已解析的独立引用。

## 10. MCP 与 REST 接口

### MCP Tools

- `search_once`：执行第一轮八源并发和社区定向搜索。
- `research`：执行第一轮并根据结果自动延伸。
- `continue_research`：基于现有 `request_id` 追加维度或追问。
- `get_research_result`：获取后台补全后的最终结果。
- `provider_status`：查看来源健康度、队列和最近错误摘要。

### REST

- `POST /v1/search`
- `POST /v1/research`
- `POST /v1/research/{id}/continue`
- `GET /v1/research/{id}`
- `GET /v1/providers/status`
- `GET /healthz`
- `GET /readyz`（鉴权后脱敏）
- `/mcp`：MCP Streamable HTTP 入口，支持 POST/GET/DELETE 会话语义。

默认 `research` 返回后台任务 `request_id`，并可通过 `wait_seconds` 等待一个短窗口。浏览器来源拥堵时继续轮询同一任务，不把排队状态伪装成已完成结果。

## 11. 并发、队列与缓存

### 11.1 家庭用户容量

初始容量策略：

- 5–10 个独立客户端 Key。
- 每个 Key 最多同时运行 1 个完整研究任务。
- 全局最多 2 个活跃完整研究任务，超出后进入有界队列；队列等待超时返回 `429`。
- API Provider 和浏览器 Provider 继续使用各自实测 Semaphore、超时和取消清理。
- 每次完整研究启动八个 Provider 的两条 lane，共 16 个 Provider Job。

该限制来自本机真实容量：一轮完整研究会占用 2 个千问任务，而千问实测 `active_limit=5`。20 个逻辑客户端可同时完成鉴权和轻量请求，不代表 20 个完整研究同时执行。

2026-07-24 网关验收：本地 20 个认证客户端 20/20 完成，p50 0.506 秒、p95 0.599 秒；Cloudflare 公网路径 20/20 完成，p50 2.076 秒、p95 2.836 秒。另有 mock 研究测试证明 20 个提交者下实际活跃完整研究始终不超过 2。

### 11.2 浏览器来源

每个浏览器 Provider 暴露 20 个逻辑槽位，但生产 `active_limit` 只能使用通过唯一标记、无串线和独立会话 URL 验收的最高等级：

| 来源 | 通过等级 | 首个失败等级 | 生产 active_limit |
| --- | --- | --- | --- |
| 豆包 | 2、5、10 | 20（仅 4/20 完成） | 10 |
| 元宝 | 2、5、10 | 20（17/20 完成） | 10 |

### 11.3 缓存

- 规范化查询缓存：避免家庭成员短时间重复搜索同一对象。
- Provider 原始结果缓存：按来源和查询隔离。
- 实体解析缓存：复用别名、官方域名和主体映射。
- 默认 TTL 按信息类型设置：实时舆情最短，工商/基础资料较长。
- 缓存命中仍显示原始采集时间，不能把旧结果表述为实时结果。

## 12. 鉴权与密钥

- 每位家庭成员生成独立客户端 Key。
- 客户端通过 `Authorization: Bearer <key>` 访问。
- 服务端只保存客户端 Key 的加盐哈希、标签、权限、并发额度和撤销状态。
- 上游模型、Tavily、Exa、GitHub 等凭证只保存在本机私密配置或系统 Keychain。
- MCP/Skill 分发包只包含服务地址和设置说明，不包含共享上游凭证。
- 日志对 `Authorization`、Cookie、API Key、Profile 路径和敏感响应字段进行清洗。
- 提供单 Key 撤销和轮换，不影响其他家庭成员。
- Cloudflare 可额外启用 Access 作为第二层保护，但应用层 Key 验证不可省略。

用户在聊天中发送过的上游 Key 不进入任何文件，应在实施前轮换为新 Key。

## 13. 客户端 Skill

### ZCode

- 注册远程 MCP URL。
- 安装 `multi-search-remote` Skill。
- Skill 判断何时使用 `search_once`、`research` 或 `continue_research`。
- Skill 保留来源、冲突和置信度字段，并让 ZCode 根据用户问题组织最终输出。

### WorkBuddy 和仅支持 Skills 的客户端

分发包包含：

```text
multi-search-remote/
├── SKILL.md
├── README.md
├── setup.sh
├── scripts/
│   └── remote_search.py
└── templates/
```

`remote_search.py` 使用 HTTPS REST 调用远程服务。客户端 Key 存在本机私密配置，不写进 `SKILL.md`。Skill 会：

1. 提取用户原始目标，而不是自行生成无界关键词。
2. 调用服务端自动研究。
3. 在服务端建议延伸搜索且预算允许时调用 `continue_research`。
4. 将结构化 Claim、Citation、Conflict 和 Unknown 交给客户端 AI。
5. 明确展示置信度和未验证信息。

## 14. 失败与降级

- 单 Provider 失败：记录错误，其他来源继续。
- 浏览器队列拥堵：返回快速部分结果，后台补全。
- AI Planner 失败：使用规则化基础查询并运行八源搜索。
- AI Verifier 失败：返回规范化来源和未验证 Claim，不伪造置信度解释。
- 上游限流：指数退避、熔断并显示下一次可用时间。
- Cloudflare Tunnel 中断：本地健康检查仍可诊断，LaunchAgent 自动重启 Tunnel。
- 来源全部失败：返回明确失败状态，不生成看似完整的答案。

## 15. 可观测性

记录但不泄露敏感数据的指标：

- 每个请求总耗时、快速结果耗时和最终结果耗时。
- 每个 Provider 的执行时间、排队时间、成功率和超时率。
- API 限流、浏览器登录失效和验证码状态。
- 缓存命中率。
- 每个客户端 Key 的并发数和调用量。
- `partial` 结果比例。
- Claim 的引用完整率和无来源 Claim 数量。

运行目标：

- API 快速路径不等待浏览器队列。
- 单来源故障不导致整个研究失败。
- 任何高置信 Claim 必须至少关联一份可解释的证据。
- 服务不记录完整访问 Key、Cookie 或上游密钥。

## 17. 现有包的复用与重构边界

复用：

- Provider 搜索实现中仍然有效的适配逻辑。
- Research Brief、URL 去重、证据角色和 Citation Ledger 思路。
- 私密状态捕获和文件权限处理中的安全做法。
- 现有 Gemini、Grok、豆包、元宝、文心、千问、Tavily、Exa Provider 经验。

重构：

- 将硬编码 Provider Runner 改为统一 Adapter 接口。
- 从本地 stdio 单进程改为远程 Streamable HTTP + REST。
- 从进程全局锁改为 Provider/账号级队列和 Worker。
- 增加客户端鉴权、配额、缓存、任务状态和可观测性。
- 增加 GitHub 等社区 Adapter。
- 增加 DeepSeek Planner、Router、Verifier 和 Synthesizer。
- 移除与搜索 Skill 无关、可能污染调用方指令的文档内容。

9. 增加 LaunchAgent、Cloudflare ingress 和健康检查。

11. 输出不含密钥的可移植安装包和家庭成员使用说明。

## 19. 最终决策摘要

- 使用方案 B，而不是直接给现有 stdio 服务加公网入口。
- 八个通用来源每次第一轮同时启动。
- 社区定向搜索与通用搜索同时启动。
- 由 AI 自动理解实体、猜测意图并有限度地延伸搜索。
- 国内短视频和消费现场问题提高豆包权重，但官方事实始终以原始官方来源优先。
- 每个消费账号只对应一个浏览器进程；多人速度依靠独立 Page/Context、实测 `active_limit`、API 并发和快速部分结果保证。
- 服务端提供结构化证据、置信度和免责声明，客户端 AI 负责最终表达。
- 使用 `mcp-search.bri-king.com`，复用现有 Cloudflare Tunnel，服务仅监听本机回环地址。
